# 0006: パス操作を構文木の上で行い、Delete と ParseValue を API に足し、パス操作の誤りに L401〜L403 を割り当てる

## コンテキスト

仕様ドラフト v0.1「パスとCLI」は、パスを `/` で区切ったセグメントの列とし、書き方を参照（`&…`）の中身と同じにすると定めている。レコードではキー、コレクションではラベルで 1 段進み、リストの要素は指せない。API 一覧には `(*File).Get(path) (Value, error)` と `(*File).Set(path, v Value) error` があり、`Set` は構文木を書き換えるのでコメントが残る。`set` は途中のレコードやコレクションを作らずエラーにし、値に `{ … }` を書くと、親がコレクションなら要素の追加になる。

決まっていないことは次の 4 つ。

- `del` に当たる Go の関数。CLI の `lkal del` だけがある。
- CLI の `set` が受け取る値のテキスト（`'"ghcr.io/acme/web:1.5.0"'`、`'{ number = 80 }'`）を `Value` にする関数。
- 置き換えと追加の位置、コメントと空行の扱い。
- パス操作の誤りのコードと表示。仕様の CLI は `--json` でエラーを `{"file","line","col","code","message","hint"}` の配列にするので、コードがないと形がそろわない。

## 決定

1. `path.go` に `Get`、`Set`、`Delete`、`ParseValue` を置く。`(*File).Delete(path string) error` と `ParseValue(src []byte) (Value, error)` を仕様の API 一覧に足す。
2. パスの構文は参照の本文と同じにする。セグメントは `[A-Za-z0-9_.-]+` か引用符付きの文字列で、`/` で区切る。空のパス、空のセグメント、先頭や末尾の `/` は L401 にする。
3. `Get` は `Data()` のその位置の値を返す。代入なら値、レコードの項目と要素ならレコード、コレクションのキーならコレクションである。
4. `Set` は、パスと値を検査してから構文木を書き換える。誤りがあれば何も変えない。
    - 親（最後のセグメントを除いた部分）はレコードかコレクションでなければならない。たどれなければ L402。
    - 親がレコードなら、最後のセグメントはキーである。値の種類で項目の種類が決まる（コレクションは要素の並び、レコードはブロック、それ以外は代入）。キーがあれば、最初の項目の位置で置き換え、その項目のコメントと空行を引き継ぐ。なければブロックの最後の項目の後ろ（末尾のコメントの前）に足す。
    - 親がコレクションなら、最後のセグメントはラベルで、値はレコードでなければならない（L403）。ラベルがあれば本体を置き換え、なければ最後の要素の直後に足す（意味規則 3 の「要素は連続させる」を保つ）。
    - ブロックやリストを同じ種類で置き換えたときは、1 行か複数行かの選択を引き継ぐ。新しく作るブロックは複数行、リストは 1 行にする（[[0004]] と同じ）。
    - 10 進数と量の数値は正規化して持つ。
5. `Delete` は、項目をコメントごと消す。コレクションのキーなら要素をすべて、ラベルならその要素を消し、最後の要素を消したらコレクションもなくなる。消した項目の前に空行があれば、次の項目にその空行を移す。
6. `ParseValue` は、代入の右辺と同じ値（スカラー、リスト、`\\` 行）、`{ … }`（レコード）、`"label" { … }` の並び（コレクション）を受け付ける。前後の空行とコメント行は読み飛ばす。誤りは `Parse` と同じ形（`File` は空文字列、位置は値のテキストの中）で返す。`get` の出力（`FormatValue`、[[0005]]）を `set` にそのまま渡せる。
7. パス操作の誤りに次の 3 つのコードを追加する（L4xx を「パス操作」の範囲とする）。

    | コード | 内容 | hint |
    | --- | --- | --- |
    | L401 | パスの書式の誤り | separate segments with / and quote segments that contain other characters |
    | L402 | パスの先に項目がない（代入の値の中へ進もうとした場合を含む） | check the path at segment "<セグメント>" |
    | L403 | `Set` に渡した値が LKAL のデータとして正しくない、またはその位置に置けない | 問題ごとに直し方を示す（nil、10 進数・量・列挙子・参照の書式、100 桁超、不正な UTF-8、リストの中の入れ物、型の混ざったリスト、`$` のキー、キーやラベルの重複、空のコレクション、要素がレコードでない） |

8. `Get`、`Set`、`Delete` の誤りは、`*Error` を 1 つ持つ `*ErrorList` で返す。`File` は文書の名前、位置はなし（`Pos` はゼロ値）とし、表示は `web.lkal: L402 path not found` の形になる（[[0004]] の表示規則）。

## 根拠（調査結果・出典）

- 仕様ドラフト v0.1「パスとCLI」: パスの書き方、`set` の振る舞い（親がないときのエラー、`{ … }` による要素の追加、コメントが残ること）、`lkal del` の存在、`--json` の出力形式。
- 同「データモデル」の意味規則 1〜6: `Set` の後も、重複、種類の衝突、要素の連続、`$` のキー、型の揃ったリストを満たす必要がある。値を検査してから書き換えれば、書き換えの後に文書全体を検査し直さなくてよい。
- 同「エラーメッセージ」: エラーを「位置・コード・何が悪いか・どう直すか」の形で出し、LLM の修正ループにそのまま渡せるようにする。

## 検討した代替案

- **パス操作の誤りをコードのない Go の error にする**: CLI の `--json` の出力でコードが空になり、修正ループで扱いにくい。ユーザーの判断でコードを付けることにした（2026-10-13）。
- **値の誤りに既存の L2xx を使う（型の混ざったリストなら L204）**: `Set` に渡す値には位置がなく、プログラムの呼び出しの誤りである。どの問題でも同じ L403 にし、hint で直し方を分ける。
- **`Set` の後に文書全体を `Format` して `Parse` し直して検査する**: 誤りの位置が、利用者の書いていないテキストを指す。値を先に検査するほうが原因を示せる。
- **`del` を `Set(path, nil)` で表す**: nil を「消す」の意味に使うと、nil を渡す誤りと区別できない。仕様は null のような「値がない」状態を持たない（原則 3）。
- **新しい項目をキーの順や種類でまとめて差し込む**: 書き手の記述順を保つ（正準形）という考え方に合わない。追加は末尾、要素は同じコレクションの最後の直後に置く。

## 影響とトレードオフ

- 得るもの: エージェントがテキストを直接編集せずに、`get` / `set` / `del` で値を読み書きできる。コメントと書き手の選択（記述順、1 行か複数行か）が残る。
- 失うもの: 置き換えたブロックの中のコメントは消える。`set` で書き換えたファイルは全体が正準形になる。
- リスク: L401〜L403 は一度公開すると変えられない。ユーザーの確認を受けて accepted にした（2026-10-13）。
- 今後: リストの要素を指すパスと、途中の項目を作る `set` は v0.1 の範囲外で、仕様の改訂で扱う。
