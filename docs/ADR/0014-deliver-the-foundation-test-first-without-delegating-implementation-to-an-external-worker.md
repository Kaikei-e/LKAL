# 0014: 実装を外部のワーカーに委譲せず、テストを先に書いて RED と GREEN を別コミットにする

## コンテキスト

[[0003]] は、基礎（[[0001]]）の実装を外部のワーカーに委譲する運用と、テストを先に書いて RED と GREEN を別コミットにする進め方を、ひとつの決定として定めた。

委譲に使っていた仕組みは、使うのをやめた。ホスト（Claude Code または Codex）が実装・テスト・調査を自分で行う。テストを先に書く進め方は、委譲をやめても変わらず必要である。

制約は次の通り。

- 仕様ドラフトは `docs/internal/` に置き、`.gitignore` で除外している（公開リポジトリに載せない）。非公開の仕様書はコピーもコミットもしない（追跡ドキュメントには個人環境の絶対パスを含めない）。
- 個人環境に依存する設定（`.mcp.json`、`.codex/`、`.claude/settings.local.json`）は Git 管理しない。

## 決定

- 実装・テスト・調査は、ホストが自分で行う。外部のワーカーへの委譲と、そのための MCP サーバーの登録はしない。
- 実装はテストを先に書いて進める。
    1. **RED**: 意図した振る舞いを正確なテストで固定し、テストがコンパイルできることと `gofmt` の出力が空であることを確かめる。テストの合格は求めない。
    2. **GREEN**: 実装を書き、`go test -count=1 ./...` と `go vet ./...` が通り、`gofmt -l .` の出力が空であることを確かめる。
- RED（テスト）と GREEN（実装）は別のコミットにする。push はしない。
- 差分と仕様を Opus レビュー（Claude Code のサブエージェント）で突き合わせ、RED では「テストが仕様どおりか」、GREEN では「テストを弱めていないか」を見る。

## 根拠（調査結果・出典）

- 仕様ドラフト v0.1「Go実装方針」は、テストをゴールデン・性質・ファズ・適合の 4 種と定めている。テストを先に書く進め方は、これらのテストを実装より先に決めるための前提である。
- [[0003]] のもとで GREEN の後に行った Opus レビューと独立のオラクルとの照合は、テストが押さえていない退行を見つけた。レビューの価値は委譲の有無に依存しない。

## 検討した代替案

- **[[0003]] をそのまま残す**: 使わなくなった委譲の手順が、有効な決定として残り続ける。
- **テストと実装を同時に書く**: RED を確かめる時点がなく、実装に合わせてテストを書く形になりやすい。TDD の意味がなくなる。

## 影響とトレードオフ

- 得るもの: 有効な決定から委譲の手順が消え、テストを先に書く進め方だけが残る。
- 失うもの: 並列のワーカーに作業を分けられない。大きな作業はホストが順に進めるので、時間がかかる。
- リスク: テストを通すためにテストを弱める変更は、GREEN のレビューで差し戻す。
