# 0009: ブロックの入れ子を 1000 段までにし、超えたら L107 にする

## コンテキスト

仕様ドラフト v0.1 は、ブロック（`{ … }`）の入れ子の深さを制限していない。いっぽう「JSONとの対応」は、LKAL から LKAL-JSON への変換がどの文書でも成功すると定めている。

[[0008]] で `ToJSON` は `encoding/json/jsontext` で書くことにした。jsontext は入れ子を 10000 段までに制限しており、この上限は go1.27.2 では変えられない（`maxNestingDepth` は定数）。LKAL のレコード 1 段は JSON の 1 段になる。コレクションの要素 1 段は、`{"$coll": {ラベル: レコード}}` で JSON の 3 段になる。そのため、レコードを約 1 万段、または要素を約 5000 段入れ子にした文書は `Parse` を通るのに、`ToJSON` が失敗する（Opus レビューで、実際に動かして確認した）。

パーサー、意味規則の検査、データモデルの組み立て、正準形の出力は、どれも入れ子 1 段ごとに再帰する。深さに上限がないと、極端に深い入力でゴルーチンのスタックを使い切り、プロセスが回復できない形で終わる恐れがある（実装レビューの指摘）。

## 決定

1. ブロックの入れ子は 1000 段までとする。トップレベルの本体を 0 段とし、レコードと要素のブロックを 1 段と数える。1001 段目を開く `{` は誤りで、新しいコード L107 を報告する。

    | コード | 内容 | hint |
    | --- | --- | --- |
    | L107 | ブロックの入れ子が深すぎる | nest blocks at most 1000 levels deep |

2. `Parse` と `ParseValue` では、L107 を構文エラーとして扱う。そのトップレベル項目の誤りは L107 の 1 件だけにし、括弧の対応を数えながら読み飛ばして、次のトップレベル項目から続ける。1001 段目より先へは再帰しない。
3. `FromJSON` では、1001 段目のブロックになるオブジェクトの `{` に L107 を報告し、その値を捨てる。
4. `Set` では、置いた後の深さが 1000 段を超える値を L403（hint は `nest blocks at most 1000 levels deep`）で拒否する。
5. この上限があれば、`ToJSON` の出力は JSON で最大およそ 3000 段に収まり、jsontext の上限（10000 段）を超えない。`Parse`、`FromJSON`、`Set` が返す File について、`ToJSON` は常に成功する。

## 根拠（調査結果・出典）

- go1.27.2 の `encoding/json/jsontext` は、10001 段目で「exceeded max depth」を返す。上限は定数で、設定で変えるオプションは公開されていない（options.go の `WithDepthLimit` はコメントアウトされている）。
- Opus レビューで次を確かめた。
    - `@lkal "0.1"` の後に `a {` を 9999 段重ねた文書は `Parse` を通るが、`ToJSON` は「exceeded max depth」で失敗する。
    - 入れ子の要素は 4999 段で失敗する。
- 宣言ファイル（Kubernetes のマニフェストに当たるもの）の入れ子は、通常 10 段に満たない。1000 段は、実用上の制限にならない大きさである。
- [[0002]] と同じく、既存のコードの意味は変えず、構文エラー（L1xx）の範囲に 1 つ足す。

## 検討した代替案

- **上限を付けず、深すぎる文書では `ToJSON` を失敗させる**: 仕様の「どの文書でも成功する」に例外ができる。再帰でスタックを使い切る問題も残る。
- **`ToJSON` だけ jsontext を使わずに書く**: `ToJSON` は成功するが、`FromJSON` は jsontext の上限で止まるので、深い文書は JSON を往復できない。スタックの問題も残る。
- **パーサーを再帰しない形に書き直す**: 深さの問題は消えるが、意味規則の検査、データモデルの組み立て、正準形の出力も再帰をやめる必要があり、変更が大きい。上限は 1 か所で決められる。
- **上限を 10000 段など大きくする**: 要素の入れ子が JSON で 3 段になるので、`ToJSON` が jsontext の上限を超えうる。

## 影響とトレードオフ

- 得るもの: `ToJSON` が常に成功するという仕様の約束を守れる。悪意のある深い入力でプロセスが落ちない。
- 失うもの: 1000 段を超える入れ子の文書を書けない。
- リスク: L107 は一度公開すると変えられない。ユーザーの確認を受けて accepted にした（2026-10-14）。
- 今後: 仕様を改訂するときに、構文の節とコード表へこの上限を取り込む。
