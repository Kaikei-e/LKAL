# 0004: LKAL-JSON との相互変換を json.go に置き、FromJSON は自前の走査で位置を決め、JSON 固有の誤りに L301〜L305 を割り当てる

## コンテキスト

基礎（[[0001]]）の次の段階として、仕様ドラフト v0.1「JSONとの対応」の `ToJSON(f *File, plain bool) ([]byte, error)` と `FromJSON(src []byte) (*File, error)` を実装する。仕様が決めているのは、タグ 4 種（`$enum` `$qty` `$ref` `$coll`）、トップレベル先頭の `"$lkal"`、逆方向で拒否する入力の種類（`$lkal` がない・未対応の版、null、指数表記、入れ子の配列、オブジェクトを含む配列、`$` で始まる通常のキー、未知のタグ）、数値を `json.Number` で文字列のまま受け取ること、キー順を保存することまでである。

決まっていないことは次の 4 つ。

- 拒否したときのエラーコードと位置。コードは版をまたいで変えない約束なので、一度決めると戻せない。
- `ToJSON` の出力の空白と改行。CLI の `lkal json` の出力がこれになる。
- `FromJSON` が返す `*File` の構文木の形。`lkal from-json` はこれを正準形で出力する（[[0005]]）。
- エラーに付けるファイル名。仕様のシグネチャは `FromJSON(src)` で、名前を受け取らない。

基礎の段階では、適合テストがテストの中に専用の変換器（`confRecordToLKALJSON` など）を持っていた。

## 決定

1. `json.go` に `ToJSON` と `FromJSON` を置く。シグネチャは仕様どおりとする。
2. `ToJSON` の出力は `json.MarshalIndent(v, "", "  ")` と同じ形（2 スペースのインデント、1 メンバー 1 行、空のオブジェクトと配列は `{}` / `[]`）に、HTML エスケープを切った文字列表現と末尾の改行 1 つを加えたものとする。`nil` の File だけがエラーになる。
3. 参照は `{"$ref": "<参照の本文>"}` とし、本文は正準形の規則 13 で書く（`[A-Za-z0-9_.-]` だけの空でないセグメントは裸、それ以外は LKAL の文字列リテラル）。plain JSON では `$lkal` を外し、列挙子は名前、量は `数値+単位`、参照は同じ本文の文字列にし、コレクションはラベルをキーにしたオブジェクトにする。
4. JSON 固有の誤りに次の 5 つのコードを追加する（L3xx を「JSON 入力」の範囲とする）。

    | コード | 内容 | hint |
    | --- | --- | --- |
    | L301 | 不正な JSON（構文、不正な UTF-8、BOM、対になっていないサロゲート、値の後ろの余分な文字） | fix the JSON syntax |
    | L302 | null | omit the key instead of writing null |
    | L303 | 指数表記の数値 | write the number without an exponent |
    | L304 | 配列の要素がスカラーでない（入れ子の配列、タグでないオブジェクト、`$coll`） | use only scalars as list elements |
    | L305 | タグの誤用（タグのオブジェクトに 2 つ目のキー、ペイロードの型や書式の誤り、空の `$coll`、要素がレコードでない `$coll`） | タグごとに例を示す |

5. LKAL のテキストと同じ規則に違反する誤りは既存のコードを使う。桁数と int64 の範囲は L005、`$lkal` がない・先頭にない・文字列でない・2 回以上ある、またはトップレベルがオブジェクトでないときは L105（hint は `start the top-level object with "$lkal": "0.1"`）、版が `"0.1"` でなければ L207、同じキーやラベルの重複は L201、型の混ざった配列は L204、`$` で始まる通常のキー（`$schema` のような未知の先頭キーと、2 番目以降に現れたタグ名を含む）は L205。
6. エラーの位置は [[0002]] の規則（行は LF 区切り、列はコードポイント数）を JSON のソースに当てはめ、問題のトークンの先頭（キーや文字列の `"`、数値やリテラルの先頭、配列やオブジェクトの括弧）とする。L301 は「入力が正しい JSON の接頭辞でなくなる最初のバイト」、途中で入力が終わったときは入力の末尾の位置とする。
7. `FromJSON` は JSON を自前で走査する（標準ライブラリだけで書く）。構文エラーで読むのをやめ、それまでの誤りは残す。値ごとの誤りでは、その値を捨てて続きを読む。エラーは `Parse` と同じ順に並べて 20 件までにする。
8. `FromJSON` のエラーの `File` は空文字列とし、`(*Error).Error()` は `File` が空なら `File:` を、位置がなければ（`Pos.Line == 0`）`行:列:` を省く。CLI はファイル名を後から入れる（[[0007]]）。
9. `FromJSON` が返す構文木は正準形の材料にする。コメントと空行はなく、レコードと要素のブロックは複数行、リストは 1 行、文字列は普通のスカラーとして持ち、`\\` 行にするかどうかは整形のときに中身で決める（[[0005]]）。値から構文木を作る関数（`blockFromRecord` と `nodeFromValue`）はパス操作（[[0006]]）も使う。
10. 適合テストは `ToJSON` を使うように改め、テスト専用の変換器とその検査を消す。`FromJSON` の正常系（既存の `valid/*.json` を読んで、対の `.lkal` とデータモデルが等しいこと）、plain JSON、`FromJSON` の誤り（`json-invalid/*.json` と `.err`）の適合テストを加える。

## 根拠（調査結果・出典）

- 仕様ドラフト v0.1「JSONとの対応」は、LKAL から LKAL-JSON への変換が常に成功して単射であること、逆方向で拒否する入力の種類、キー順の保存、数値を `json.Number` で受け取ることを定めているが、エラーコードは定めていない。
- 同「エラーメッセージ」は、コードを版をまたいで変えないこと、L0xx を字句、L1xx を構文、L2xx を意味規則とすることを定めている。既存コードの意味を変えずに範囲を足すのは、[[0002]] と同じやり方である。
- Go 1.26.8 で `encoding/json` の `Decoder.Token` を試すと、`SyntaxError.Offset` の指す位置が誤りの種類によって違った（`{"a": }` は誤りの文字そのもの、`{"a": tru}` はその 1 つ後、`{"a": 1} x` は 2 つ目の値の先頭からの相対で 5）。閉じていない `{"a": 1` では、エラーではなく `io.EOF` が返った。この挙動では位置の期待値をほかの言語の実装と揃えられない。
- RFC 8259 は JSON テキストを UTF-8 とし、BOM を付けてはならないと定めている（[RFC 8259 §8.1](https://www.rfc-editor.org/rfc/rfc8259#section-8.1)）。対になっていないサロゲートを含む文字列は「予測できない振る舞い」になりうると書いている（[§8.2](https://www.rfc-editor.org/rfc/rfc8259#section-8.2)）。LKAL の文字列は Unicode のスカラー値だけを持つので、L301 で拒否する。

## 検討した代替案

- **JSON の誤りもすべて新しいコードにする**: 同じ規則（キーの重複、型の混ざったリスト、`$` のキー、版）にテキストと JSON で別のコードが付き、修正ループの側で 2 通りの直し方を覚えることになる。規則が同じなら同じコードにする。
- **`encoding/json` の `Decoder.Token` で読み、位置は `InputOffset` から推定する**: 上のとおり、構文エラーの位置が誤りの種類によってずれ、未完の入力を検出できない。位置を適合テストの期待値にできないので採らない。
- **`FromJSON(name, src)` にしてファイル名を受け取る**: エラー表示は自然になるが、仕様の API 一覧と違う形になる。CLI でファイル名を入れれば足りるので、仕様のシグネチャを保つ。
- **`$lkal` をトップレベルのどこに置いても受け付ける**: LKAL のテキストでは版の宣言を先頭に置く規則（L105）があり、JSON でも先頭に置けば版を読んでから本文を読める。位置を問わない規則は、テキストと JSON で扱いを分けることになるので採らない。
- **`ToJSON` をコンパクトな 1 行で出す**: 差分が読みにくく、適合テストの期待値ファイルとも形が合わない。

## 影響とトレードオフ

- 得るもの: LKAL → LKAL-JSON → LKAL の往復を、性質テストとファズで確かめられる。JSON の誤りにもテキストと同じ形（位置・コード・hint）のエラーが付く。
- 失うもの: JSON の走査器を自前で持つので、`encoding/json` より保守するコードが増える。
- リスク: L301〜L305 は一度公開すると変えられない。ユーザーの確認を受けて accepted にした（2026-10-13）。
- 今後: 仕様を改訂するときに、コード表と「JSONとの対応」へこの ADR の内容を取り込む。
