# 0010: Collection を Record に統合し、基数・指数表記の拒否と CLI のストリーム対応を導入する

## コンテキスト

2026-10-14 の設計レビュー（`docs/internal/lkal-review-2026-10-14.md`）において、仕様ドラフト v0.1 と Go リファレンス実装に関して次の 4 点の課題が確認された。

1. **`Record` と `Collection` の分離による不整合（提言 A-1）**:
   - データモデルで `Record` と `Collection` を別型として分離した結果、空コレクションを表現できず、要素をすべて `del` したあと `set` で第 1 要素を追加できない（0 要素境界での非対称性）。
   - `L202`（種類の衝突）・`L203`（非連続なコレクション項目）・`L206`（要素へのスカラー代入）といった人工的な意味規則や、LKAL-JSON の `$coll` タグが必要になっていた。
2. **数値・量の字句解析における基数接頭辞・指数表記の誤解釈（提言 B）**:
   - `0xFF` や `0b`、`0o` が「整数 `0` ＋単位 `xFF`」の `Quantity` として受理され、`0x10` や `1e5`、`1e-5` が単位エラー `L004` または不正なトークンとして一貫しない扱いになっていた。
3. **CLI のストリームフィルタ対応の欠落（提言 C）**:
   - `cmd/lkal` の各サブコマンドが物理ファイルパス専用になっており、標準入力（`-`）からの読み込み、`set -` / `del -` の標準出力への書き出し、`get -r` による引用符なし生出力ができなかった。
4. **スキーマ非依存の等価性の保証（提言 D）**:
   - 仕様ドラフトに「v0.2 のスキーマで順序付きコレクションを宣言できるようにする」という記述があり、`lkal.Equal` の同値関係がスキーマの有無で分裂する懸念があった。

## 決定

1. **提言 A-1（`Collection` の `Record` への統合と複数ラベル・ラベル付き代入の解禁）**:
   - 文法を `Entry = Key { Label } ( Assign | Block ) .` に改め、0 個以上のラベルを持つブロックおよび代入をすべて認める。
   - データモデルから `Collection`（および `Elem`）を廃止し、ラベル付き項目は入れ子の `Record` の糖衣構文（パス圧縮）として展開する。たとえば `service "web" { replicas = 3 }` は `service { web { replicas = 3 } }` と同じ `Record` になる。
   - 構文木（`File`）は元のラベル列を保持し、`Format` や `Set` / `Delete` で既存の記述スタイルを維持する。また、未存在の多段パスに対する `Set` はラベル付き項目として追加できるようにする。
   - LKAL-JSON から `$coll` タグを廃止し、予約タグを `$lkal`・`$enum`・`$qty`・`$ref` に整理する。
   - エラーコード `L202`・`L203`・`L206` を廃止し、キーまたはパスの重複・衝突はすべて `L201` で報告する。`$` で始まるラベルは `Record` のキーになるため `L205`（`Set` では `L403`）で拒否する。
2. **提言 B（基数接頭辞・指数表記の `L009` による拒否）**:
   - `lexer.go` の `lexValidateNumber`（および `path.go` の `validateValue`）において、`0` または `-0` の直後に `[xXbBoO]` が続くトークン（`0xFF`, `0x10`, `0b10`, `0o77` など）と、整数・小数の直後に `[eE][+-]?[0-9]` が続く指数表記（`1e5`, `1e-5`, `1.5e3` など）を `L009`（`malformed token`）として拒否する。
3. **提言 C（CLI の標準入出力ストリーム対応と `get -r`）**:
   - すべてのサブコマンド（`fmt`, `check`, `json`, `from-json`, `get`, `set`, `del`）で `FILE` に `-` を指定したとき標準入力から読み込む。`fmt -w -` は終了コード 2 で拒否する。
   - `lkal set - PATH VALUE` と `lkal del - PATH` は、書き換え後の正準形 LKAL を標準出力に書き出す（通常のファイルパス指定時は従来どおり in-place 上書き）。
   - `lkal get -r` フラグを追加し、スカラー値（`String`, `Enum`, `Ref` などの引用符や先頭記号 `.` / `&`）を除いた生の文字列を出力する。
4. **提言 D（`lkal.Equal` の純粋関数性の維持）**:
   - 仕様ドラフトから v0.2 の「順序付きコレクション」構想を削除し、`lkal.Equal` は外部スキーマに一切依存しない純粋関数であることを不変条件とする。

## 根拠（調査結果・出典）

- `docs/internal/lkal-review-2026-10-14.md` における設計検証と赤入れ。
- HCL / Terraform でもラベル付きブロック（`resource "aws_instance" "web" { ... }`）は JSON 表現（`.tf.json`）において単なるネストした JSON オブジェクトに写像されており、特別タグなしで JSON 往復と `set` / `del` の完結性が成り立つ。

## 検討した代替案

- **10 型（`Collection`）を維持したまま `File.Set` のみ中間ノード生成を許す案（提言 A-2）**: 0 要素時の `set` は動くようになるが、JSON 往復で空のコレクションが `Record` に化ける問題や `$coll` タグの複雑さが残るため、提言 A-1 を採用した。
- **`lkal set` / `lkal del` のデフォルトを `stdout` 出力に変え `-w` フラグを新設する案**: 既存の CLI 呼び出しとの互換性を保つため、ファイルパス指定時は in-place 上書きを維持し、`FILE` が `-` のときのみ `stdout` に出力する方式を採用した。

## 影響とトレードオフ

- 得るもの: データモデルが 9 型・JSON 値タグが 3 種に単純化され、`FromJSON(ToJSON(f, false))` と `set` / `del` の往復が 0 要素境界を含めて完全に閉じる。UNIX パイプラインで `lkal` コマンドを合成できる。
- 失うもの: データモデル上で「波括弧で書かれた `a { b { ... } }`」と「ラベルで書かれた `a "b" { ... }`」を区別しなくなる（構文木では保持するため整形では区別される）。
- リスク: ラベル 1 つが `Record` 1 段に展開されるため、[[0009]] の入れ子上限（1000 段、`L107`）は波括弧とラベルの合計段数に対して適用する。
