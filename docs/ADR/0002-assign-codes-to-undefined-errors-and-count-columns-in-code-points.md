# 0002: 仕様にコードのない誤りに L007〜L009 と L106 を割り当て、列番号を Unicode コードポイントで数える

## コンテキスト

仕様ドラフト v0.1「エラーメッセージ」は、エラーを `file:line:col: コード メッセージ` と `hint:` の形で出し、コードを版をまたいで変えないと定めている。コード表は L001〜L006（字句）、L101〜L105（構文）、L201〜L207（意味規則）の 18 個である。

基礎（[[0001]]）のテストを書くために字句・構文の誤りを洗い出すと、仕様が「エラーにする」と書きながらコードを決めていないものと、どの規則にも当てはまらないものが見つかった。

| 誤りの例 | 仕様の記述 | 対応するコード |
| --- | --- | --- |
| `"web` のまま行末に達する | 文字列は「生の改行は含めない」 | なし |
| 文字列の中のタブ以外の制御文字 | 「そのまま書くとエラー」 | なし（L003 はエスケープ） |
| 先頭の BOM、不正な UTF-8 | 「UTF-8のみ。BOMは書けない」 | なし |
| `%` `;` `+` など記号表にない文字 | 記号表にない | なし |
| `01`、`1.`、`&a//b`、`.` だけ、`&` だけ | トークン規則に合わない | なし |
| `a 1`、`a = 1 b = 2`、`[[1]]`、`true = 1` | 文法に合わない | なし |

列番号の単位（バイトか文字か）も決まっていない。適合テスト（仕様「Go実装方針」のテスト 4）は実装に依存しない「入力と期待出力」の組なので、エラー位置を期待値に含めるなら、単位を決めないとほかの言語の実装と結果が合わない。コメントや文字列には日本語がよく入り、バイトと文字では列番号が大きくずれる。

## 決定

1. 次の 4 つのコードを追加する。既存の 18 個の意味は変えない。

    | コード | 内容 | 直し方（hint） |
    | --- | --- | --- |
    | L007 | 閉じていない文字列（行末か文書末までに `"` がない） | 同じ行で `"` を閉じる。複数行の文字列は `\\` 行で書く |
    | L008 | 使えない文字（BOM、不正な UTF-8、文字列の中のタブ以外の制御文字、記号表にない文字） | 文字を消す。制御文字は `\u{…}` で書く |
    | L009 | 数値・列挙子・参照・ディレクティブの形の崩れ（`01`、`1.`、`-` だけ、`.` だけ、`&` だけ、空のセグメント、`@` だけ） | トークン規則の形に直す |
    | L106 | 文法に合わないトークン（上の表の構文の例、予約語のキー、ネストしたリスト、区切りのない項目） | 期待したトークンを示す。予約語をキーにするなら引用符で囲む |

2. 列番号は 1 から始まり、行頭からの Unicode コードポイント数で数える。タブも 1 つと数える。行番号は 1 から始まり、LF で区切る（CRLF は LF と同じに扱う）。

3. 1 つの誤りに複数のコードが当てはまるときは、個別のコードを優先する。L106 は、ほかのどのコードにも当たらないときだけ使う。

## 根拠（調査結果・出典）

- 仕様「エラーメッセージ」には「コードは版をまたいで変えない。L0xxが字句、L1xxが構文、L2xxが意味規則のエラーである」とある。追加は既存コードの意味を変えないので、この規則と両立する。
- 仕様「字句規則」の補足は「UTF-8のみ。BOMは書けない」「タブ以外の制御文字をそのまま書くとエラー」と書くが、コード表に対応するコードがない。
- Go の `go/token.Position.Column` は「column number, starting at 1 (byte count)」で、バイト数を数える（`go doc go/token.Position`、Go 1.26.8 で確認）。
- LSP 3.17 は列のエンコーディングを交渉で決め、既定は UTF-16、ほかに UTF-8 と UTF-32 を定義している（[LSP 3.17 仕様 PositionEncodingKind](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#positionEncodingKind)）。コードポイント数は UTF-32 のコード単位数と同じなので、LSP に対応するときもそのまま渡せる。

## 検討した代替案

- **列をバイトで数える（Go の慣習）**: Go のツールとは揃うが、日本語のコメントや文字列より後ろの誤りで、人が数える位置と大きくずれる。エラーを読むのは人と LLM の修正ループで、どちらも文字で数えるほうが自然なので採らない。
- **列を UTF-16 コード単位で数える（LSP の既定）**: エディタ連携には便利だが、言語ごとに実装の手間が違い、適合テストの期待値として不自然である。LSP 対応は変換で済むので採らない。
- **汎用の構文エラーを既存の L102 に寄せる**: L102 は「値の位置の裸の単語」で hint も固有なので、関係のない誤りに同じ hint が付く。採らない。
- **字句の誤りを 1 つのコードにまとめる**: 修正ループに渡したとき、閉じ忘れと不正な文字と形の崩れでは直し方が違う。3 つに分ける。
- **`L000` のような汎用コードだけで済ませる**: コードを版をまたいで変えない約束の下では、後から細分化できなくなる。採らない。

## 影響とトレードオフ

- 得るもの: 基礎のテストと適合テストで、すべての誤りにコードと位置の期待値を書ける。
- 失うもの: 仕様ドラフトのコード表とこの ADR の 2 か所を見る必要がある。仕様を改訂するときに、この表を取り込む。
- リスク: コードは版をまたいで変えないので、一度公開すると戻せない。そのため状態を proposed にして、RED テストを書く前に確認を受ける。
- 実装への影響: Go 実装は、行内のバイト位置からコードポイント数を数え直す（`unicode/utf8` の `RuneCount` など）。
