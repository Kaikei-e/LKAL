# 0013: lkal check --schema、lkal set --schema、lkal schema check を CLI に追加し、--json 出力に path を含める

## コンテキスト

[[0011]] と [[0012]] により、`github.com/Kaikei-e/LKAL/schema` パッケージでスキーマのコンパイルとデータ文書の検証が可能になった。これを CLI（`cmd/lkal`、[[0007]]、[[0010]]）から利用できるようにするため、次の 4 点を決める必要がある。

1. 既存の `lkal check` でスキーマ検証をどのように指定し、スキーマ自体の読み込み失敗（I/O エラー）とスキーマ定義エラー（`L601`〜`L607`）の終了コードをどう区別するか。
2. エージェントや自動化スクリプトが `lkal set` で値を書き換える際、スキーマ違反を起こす変更をファイル上書き前に防ぐ仕組み。
3. データ文書なしでスキーマ文書単体の妥当性を検査するサブコマンドの形。
4. [[0012]] で追加した `Error.Path` を、`--json` フラグ指定時の JSON エラー配列に後方互換を保って出力する方法。

## 決定

### 1. `lkal check [--schema S] [--json] FILE...` の拡張

- `lkal check` に `--schema S`（または `-schema S`）フラグを追加する。
- `--schema S` が指定された場合、データファイルの検査に入る前にスキーマファイル `S` を読み込み、`schema.Compile` でコンパイルする。
  - `S` が空文字列、またはファイルの読み込みに失敗した場合は、使い方・I/O の誤りとして標準エラー出力にメッセージを出し、終了コード `2` で終了する（[[0007]] の終了コード規則に従う）。
  - `S` の構文・意味規則エラーまたはスキーマコンパイルエラー（`L601`〜`L607`）が発生した場合は、そのエラーを標準エラー出力（`--json` 時は JSON 配列）に出力し、終了コード `1` で終了する。
- スキーマのコンパイルに成功したら、各 `FILE`（`-` による標準入力を含む、[[0010]]）を順に `lkal.Parse` し、`Parse` に成功したファイルに対して `(*Schema).Validate(f)` を実行する。`Parse` でエラーが出たファイルにはスキーマ検証を重ねず、次のファイルの検査へ進む。1 件でもエラーがあれば終了コード `1` を返す。

### 2. `lkal set [--schema S] [--json] FILE PATH VALUE` の事前検証

- `lkal set` に `--schema S`（または `-schema S`）フラグを追加する。
- `--schema S` が指定された場合、`S` を先にコンパイルし（読み込み失敗は終了コード `2`、スキーマ自体のエラーは終了コード `1`）、対象 `FILE` の `Parse`・`ParseValue`・`f.Set(path, val)` がすべて成功したあと、**ファイルへの書き戻し（または `FILE` が `-` のときの標準出力への書き出し）を行う前に**、メモリ上の更新済み `*lkal.File` に対して `(*Schema).Validate(f)` を実行する。
- スキーマ検証でエラーが発生した場合は、ファイルを一切書き換えずに（`-` のときは標準出力に何も出さずに）エラーを標準エラー出力へ出し、終了コード `1` で中止する。

### 3. `lkal schema check [--json] FILE...` の新設

- スキーマ文書を単体で検査するサブコマンド `lkal schema check [--json] FILE...` を追加する。
- 1 つ以上の `FILE`（`-` による標準入力を含む）を受け取り、各ファイルに対して `schema.Compile` を実行する。成功時は何も出力せず終了コード `0`、1 件でもエラーがあればすべて出力して終了コード `1`、引数不足や未知のサブコマンド・ファイル読み込み失敗は終了コード `2` とする。

### 4. `--json` エラー出力への `path` フィールド追加

- `cmd/lkal` の JSON エラー出力構造体に `Path string` を `json:"path,omitempty"` として追加する。
  ```go
  type jsonError struct {
  	File    string `json:"file"`
  	Line    int    `json:"line"`
  	Col     int    `json:"col"`
  	Code    string `json:"code"`
  	Message string `json:"message"`
  	Hint    string `json:"hint"`
  	Path    string `json:"path,omitempty"`
  }
  ```
- これにより、`Path == ""` である v0.1 の全エラー（`L0xx`〜`L4xx`）では [[0007]] と完全に同一の 6 キー（`file`, `line`, `col`, `code`, `message`, `hint`）の JSON オブジェクトが出力され、`Path != ""` のエラーでは `"path"` キーが含まれる。

## 根拠（調査結果・出典）

- [[0007]]（公開 API を使う薄い CLI 層と終了コード 0 / 1 / 2 の分離）:
  - `cmd/lkal` は引き続きルート `lkal` パッケージと `schema` サブパッケージの公開 API のみを呼び出す薄い層に保つ。スキーマファイルの存在しないパス指定を終了コード `2`、スキーマ内容の誤り（`L601`〜`L607`）とデータ検証の誤り（`L501`〜`L510`）を終了コード `1` に分けることで、自動化ループが「呼び出し方を間違えた（2）」のか「文書またはスキーマの内容を直すべきか（1）」を確実に判別できる。
- [[0006]] および [[0010]]（`lkal set` による構文木上の編集とストリーム対応）:
  - エージェントが `lkal set --schema app.schema.lkal app.lkal service/web/replicas '"three"'` を実行した際、メモリ上で `Validate` してから書き戻すことで、不正な変更によってディスク上のファイルやパイプライン出力が壊れることを防げる。
- `json:"path,omitempty"` による後方互換性:
  - v0.1 の適合テストおよび既存スクリプトが期待する 6 キーの JSON 形式を一切壊さずに、スキーマ検証エラーの論理パスを機械可読な形で提供できる。

## 検討した代替案

- **データ検証も `lkal schema validate SCHEMA FILE...` に分離し、`lkal check` には入れない案**:
  - `lkal check` は文書の検査コマンドとしてすでに定着しており、`--schema` フラグで構文検査とスキーマ検査を一括実行できるほうが CI やパイプラインでの使い勝手が良い。また、`lkal set --schema` とフラグ名を揃えられるため、`lkal check --schema` を採用した。
- **`lkal schema` ではなく `lkal check-schema` のようなフラットなコマンド名にする案**:
  - 将来スキーマ関連のサブコマンドを拡張する余地を残しつつ、責務を明確にするため `lkal schema check` の階層形を採用した。
- **`--json` で `Path == ""` のときも `"path": ""` を常に出力する案**:
  - v0.1 の `--json` 出力（[[0007]]）のキー集合が変わり、既存の出力比較テストとの互換性が崩れるため `omitempty` とした。

## 影響とトレードオフ

- 得るもの: `lkal check --schema`、`lkal set --schema`、`lkal schema check` により、スキーマ定義の検査からデータ文書の検査、安全な in-place / ストリーム編集までを単一の `lkal` バイナリで完結できる。
- 失うもの: `lkal set --schema` は毎回スキーマをコンパイルして検証するため、`--schema` なしに比べてスキーマ検査分の処理が加わる（ただし標準ライブラリのみのメモリ内処理であり、オーバーヘッドはごく小さい）。
- リスク: `lkal schema check` で `-`（標準入力）を複数回指定した場合は、既存の `check` / `fmt` と同様に最初の `-` が標準入力を消費し、2 回目以降は空入力となる。
- 今後: `schema export` や `schema diff` などの高度なスキーマ運用コマンドは、実際の運用要件が固まった段階で別途検討する（[[0011]]）。
