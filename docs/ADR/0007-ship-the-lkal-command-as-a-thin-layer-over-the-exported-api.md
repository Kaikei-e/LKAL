# 0007: lkal コマンドを公開 API だけを使う薄い層として cmd/lkal に置き、エラーは標準エラー出力に出す

## コンテキスト

仕様ドラフト v0.1「パスとCLI」は、1 つのバイナリ `lkal` に 7 つのコマンド（`fmt`、`check`、`json`、`from-json`、`get`、`set`、`del`）をまとめ、終了コードを 0（成功）、1（検査エラー）、2（使い方の誤り）とし、`--json` でエラーを JSON の配列で出すと定めている。

決まっていないことは次の 4 つ。

- `--json` の配列を標準出力と標準エラー出力のどちらに出すか。
- ファイルの読み書きに失敗したときの終了コード。
- `set` と `del` がファイルをどう書き戻すか。
- ファイル名を持たないエラー（`FromJSON` と `ParseValue`、[[0004]] [[0006]]）の表示。

## 決定

1. `cmd/lkal/main.go` に置き、標準ライブラリとこのモジュールの公開 API だけを使う。処理は `run(args, stdin, stdout, stderr) int` にまとめ、テストはこれを一時ディレクトリのファイルで呼ぶ。
2. 各コマンドは自分のフラグを `flag.FlagSet` で読む。フラグは位置引数より前に書く。どのコマンドも `--json` を受け付ける。
3. 各コマンドの振る舞いは次のとおり。

    | コマンド | 振る舞い |
    | --- | --- |
    | `fmt [-w] [-l] FILE…` | 正準形を標準出力に出す。`-l` は正準形と違うファイルの名前だけを出し、`-w` は違うファイルを上書きする。エラーのあるファイルは書き換えず、ほかのファイルは続けて処理する |
    | `check FILE…` | すべてのファイルを検査する。成功しても何も出さない |
    | `json [--plain] FILE` | LKAL-JSON（`--plain` なら plain JSON）を出す |
    | `from-json FILE` | LKAL-JSON を読み、正準形の LKAL を出す |
    | `get FILE PATH` | 値を `FormatValue` の形で出す |
    | `set FILE PATH VALUE` | VALUE を `ParseValue` で読み、`Set` してファイルを正準形で書き戻す |
    | `del FILE PATH` | `Delete` してファイルを正準形で書き戻す |

4. 終了コードは、コード付きのエラー（字句・構文・意味規則・JSON・パス・値）が 1 件でもあれば 1、使い方の誤り（コマンドなし、未知のコマンドやフラグ、引数の数の誤り）とファイルの読み書きの失敗は 2 とする。
5. エラーは標準エラー出力に出す。標準では `Error()` の文字列を 1 件ずつ、`--json` ではすべてのエラーを 1 つの JSON 配列（1 行、キーは `file` `line` `col` `code` `message` `hint` の順、位置がなければ 0）にする。エラーがなければ何も出さない。使い方の誤りと読み書きの失敗は、`--json` でも文字列で出す。
6. ファイルから読んだ文書のエラーには、引数に書かれたファイル名を入れる。`set` の VALUE の誤りには `<value>` を入れる。

## 根拠（調査結果・出典）

- 仕様ドラフト v0.1「パスとCLI」: コマンドの一覧、終了コード、`--json` の出力形式、「エージェントはテキストを直接編集せず、`get` と `set` を使う想定」。
- `fmt` のフラグ `-w` と `-l` の意味は、Go の `gofmt`（`-l` は正準形と違うファイルを一覧にし、`-w` は書き戻す）と同じにした（`go doc cmd/gofmt`）。
- コマンドの出力（`fmt`、`json`、`get` の結果）とエラーを別の出力先に分ければ、`fmt` で一部のファイルだけが失敗したときも、標準出力には整形結果だけが残る。

## 検討した代替案

- **`--json` の配列を標準出力に出す**: `check` だけなら読みやすいが、`fmt` で複数のファイルを処理したときに整形結果と JSON が同じ出力先に混ざる。すべてのコマンドで同じ扱いにするため、標準エラー出力にする。
- **ファイルの読み書きの失敗を 1 にする**: 1 は文書の検査エラーの意味に保ち、修正ループが「文書を直せば通る」と判断できるようにする。存在しないファイルを渡すのは使い方の誤りとして 2 にする。
- **CLI の中で正準形やパスの処理を書く**: ライブラリと CLI で振る舞いがずれる。公開 API だけを使えば、CLI のテストがライブラリの公開面の結合テストにもなる。
- **`set` と `del` で、変えた行だけをテキストとして書き換える**: 構文木と元のテキストの位置を突き合わせる仕組みが要り、v0.1 では大きすぎる。書き戻しは `(*File).Format()` に任せ、ファイル全体が正準形になることを受け入れる。

## 影響とトレードオフ

- 得るもの: 7 つのコマンドが同じエラー形式と終了コードを持つ。テストはバイナリをビルドせずに `run` を呼べる。
- 失うもの: `set` と `del` は、正準形でないファイルを正準形に書き直す。手で整えた書き方（正準形の外）は残らない。
- リスク: 標準入力からの読み込み（`-` など）はない。必要になったら追加する。
