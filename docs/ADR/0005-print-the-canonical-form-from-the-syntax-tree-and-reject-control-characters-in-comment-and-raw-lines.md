# 0005: 正準形を構文木から出力し、コメント行と \\ 行のタブ以外の制御文字を L008 にする

## コンテキスト

仕様ドラフト v0.1「正準形」は、`lkal fmt` の出力を 14 の規則で決めている。書き手の選択として残すのは、項目の記述順、1 行で書くか複数行で書くか、空行の 3 つである。構文木（[[0001]]）は、コメント（直後の項目に付ける）、項目前の空行（`blankBefore`）、1 行ブロック（`oneLine`）をすでに保持している。

整形の対象になる構文木は 3 通りある。`Parse` の結果、`FromJSON` の結果（[[0004]]）、パス操作で書き換えた結果（[[0006]]）である。仕様の API 一覧にある整形関数は `Format(src []byte) ([]byte, error)` だけで、構文木を整形する公開関数がない。`lkal from-json` と `lkal set` / `del` には、それが必要になる。

仕様の空白も 1 つ残っていた。字句規則は、文字列の中のタブ以外の制御文字をエラーにすると定めているが、コメント行と `\\` 行の中の制御文字には触れていない。今の実装は、そこにある CR と不正な UTF-8 だけを L008 にし、`\x01` などは通している。正準形の規則 9 は、タブ以外の制御文字を含む文字列を `"…"` で書くとしているので、`\\` 行に制御文字があると、整形で書き方が変わる。

## 決定

1. `format.go` に次の 3 つを置く。
    - `Format(src []byte) ([]byte, error)`: 仕様どおり。`Parse("", src)` のエラーをそのまま返す。
    - `(*File).Format() []byte`: 構文木を正準形で出力する。仕様の API 一覧に足す。
    - `FormatValue(v Value) []byte`: 値 1 つを正準形の値表記で出力する。`lkal get` が使う。仕様の API 一覧に足す。
2. 正準形の規則を、構文木に対して次のように当てはめる。
    - 値は構文木に残したソースの字面ではなく、データモデルの値から出力する。数値は正規化した形になる。
    - 文字列は中身で書き方を決める（規則 9）。LF を含み、タブと LF 以外の制御文字を含まなければ `\\` 行、それ以外は `"…"`。`\\` 行 1 行だけで LF を含まない値は `"…"` になる。
    - 1 行ブロックは、入力で 1 行に書かれ、中身がコメントのない代入だけで、どの値も `\\` 行にならず、リストもすべて 1 行のときだけ 1 行で残す（規則 4）。
    - 空行は、ブロックの最初の項目の前では消し、それ以外では項目（コメントがあればその最初の行）の前に 1 行まで残す（規則 7）。版の宣言の後ろには必ず 1 行入れる（規則 14）。版の宣言より前のコメントと宣言の間の空行は、入力にあれば 1 行残す。
    - エスケープは必要なものだけにする。`"` `\` LF CR は短い形、ほかのタブ以外の制御文字は `\u{…}`（小文字の 16 進、先頭の 0 なし）、それ以外はそのまま書く。
3. コメント行（`###`、L001 になる `#` / `##` の行も含む）と `\\` 行の中の、U+0000〜U+001F のタブ以外と U+007F を、文字ごとに L008 にする。文字列の中で L008 になる集合と同じである。
4. テストは次の 4 種類にする。
    - ゴールデン: `testdata/format/*.lkal` と `*.golden`、`testdata/fromjson/*.json` と `*.golden`
    - 性質: `fmt(fmt(x)) == fmt(x)`、整形の前後でデータモデルと版が等しい、整形の前後で `ToJSON` の出力が等しい、`FromJSON(ToJSON(f))` の整形結果が `Format` の不動点になる
    - ファズ: `FuzzFormat` で、`Parse` が受け付けた入力について上の性質を確かめる
    - 字句: 制御文字の L008 の位置

## 根拠（調査結果・出典）

- 仕様ドラフト v0.1「正準形」の規則 1〜14、「設計原則」の 5（行は自己完結する）と 6（整形結果は安定している）。
- 同「字句規則」の補足は、文字列について「タブ以外の制御文字をそのまま書くとエラー」と定めている。コメント行と `\\` 行は「行末までが中身」とだけ書いている。
- 同「Go実装方針」は、構文木（`File`）をフォーマッタと `set` が使い、コメントを保持すると定めている。
- 規則 9 が `\\` 形式を許すのは、タブ以外の制御文字を含まない文字列だけである。`\\` 行が制御文字を持てなければ、`\\` 行で書いた文字列は、LF を含むかぎり整形の後も `\\` 行のままになる。

## 検討した代替案

- **コメント行と `\\` 行の制御文字を今のまま通す**: 整形で `\\` 行が `"…\u{1}…"` に書き換わり、コメントには制御文字がそのまま残る。端末に表示したときに行の中身が見えなくなるので、行は自己完結する（原則 5）という考え方に合わない。ユーザーの判断で L008 にした（2026-10-13）。
- **ソースの字面（`tok.lit`）をそのまま出す**: `1.50` や `+` の付いた表記が残り、規則 11 を満たさない。`FromJSON` やパス操作で作った構文木には字面がない。
- **`Format(src)` だけを公開し、CLI の中で文字列を組み立てる**: 正準形の規則が 2 か所に分かれ、`from-json` と `set` の出力が `fmt` とずれうる。
- **行幅で 1 行ブロックを折り返す**: 仕様が行幅に依存しないと決めている（規則 4、原則 6）。

## 影響とトレードオフ

- 得るもの: `fmt`、`from-json`、`set`、`del` が同じ出力関数を通る。性質テストとファズで冪等性とデータの保存を確かめられる。
- 失うもの: 制御文字を含むコメントや `\\` 行を持つ既存の文書はエラーになる。v0.1 はドラフトなので、互換性の問題は小さい。
- リスク: 構文木に足りない情報（宣言の前の空行など）が見つかれば、構文木とパーサーを拡張する（[[0001]] の「リスク」に書いたとおり）。
- 今後: 仕様を改訂するときに、字句規則の補足へ制御文字の扱いを書き足す。
