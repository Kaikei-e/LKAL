# 0001: LKAL v0.1 の基礎をコアライブラリに絞り、Go 標準ライブラリだけで構文木とデータモデルの2層に実装する

## コンテキスト

LKAL は、あるべき状態を宣言するためのデータ形式である。仕様ドラフト v0.1（2026-10-12。`docs/internal/` に置き、Git 管理外）は、字句規則、13 行の EBNF、10 種の値のデータモデル、意味規則 7 つ、正準形 14 規則、LKAL-JSON、パス操作と CLI、エラーコード表までを決めている。リポジトリは README と LICENSE だけの状態から始まる。

v0.1 の機能を一度に作ると、フォーマッタ・JSON・`set` が使う構文木の形を、字句解析とパーサーが固まる前に決めることになる。どの機能も「文書を正しく読めること」の上に立つので、最初の実装をどこで区切るかを決める必要がある。

仕様側の前提は次の 3 つである。

- 処理系は Go で、標準ライブラリだけで書く（仕様「概要」「Go実装方針」）。
- 文法は LL(1) で、先読み 1 トークンの手書き再帰下降で足りる（仕様「構文」）。
- 内部は構文木（`File`。コメントや空行を保持）とデータモデル（`Value`。コメントなし）の 2 層に分ける（仕様「Go実装方針」）。

## 決定

最初の実装（以下「基礎」）は、文書を読んで検査し、データモデルとして取り出すところまでとする。

| ファイル | 中身 |
| --- | --- |
| `token.go` | トークンの種類と位置 |
| `lexer.go` | 行単位で完結する字句解析 |
| `ast.go` | 構文木。コメント（直後の項目に付ける）、項目前の空行、1 行か複数行かを保持する |
| `parser.go` | 再帰下降パーサー、意味規則 1〜6 の検査、エラー回復 |
| `value.go` | データモデルの 10 型と `Equal`（意味規則 7） |
| `errors.go` | 位置・コード・メッセージ・hint を持つエラーと、まとめて返すエラーリスト |

公開 API は、仕様「Go実装方針」の一覧のうち `Parse`、`(*File).Version`、`(*File).Data`、`Equal` と値の型だけを実装する。

`Format`（正準形）、`ToJSON` / `FromJSON`、`Get` / `Set` / `del`、`cmd/lkal` は範囲に入れない。それぞれ次の段階で ADR にしてから実装する。

実装上の取り決めは次の通り。

- モジュールパスは `github.com/Kaikei-e/LKAL`、パッケージ名は `lkal` とし、ソースはリポジトリ直下に置く（仕様のディレクトリ構成どおり）。
- `go.mod` の `go` 行は 1.26 とし、外部モジュールを `require` しない。
- 構文木は、後で作るフォーマッタと `set` に要る情報（コメント、項目前の空行、ブロックとリストを 1 行で書いたか）を基礎の段階から保持する。
- 数値は浮動小数点を経由しない。`Decimal` と `Quantity` の数値部は、仕様の正準形規則 11 で正規化した文字列で持つ。

## 根拠（調査結果・出典）

- 仕様ドラフト v0.1「Go実装方針」は、ファイル構成、`Value` の 10 型、公開 API の一覧、テスト 4 種、エラー回復（次のトップレベル項目まで読み飛ばし、最大 20 件）を定めている。基礎の範囲は、この API 一覧のうち `Parse` から `Equal` までにあたる。
- 同「構文」によれば、EBNF は 13 行で、キーの次の 1 トークンで項目の種類が決まる。パーサー生成器を持ち込む理由がない。
- 同「v0.1の範囲」では、フォーマッタ・JSON 往復・パス操作も v0.1 に入るが、どれも `Parse` の結果を入力にとる。
- 10 進数は文字列で正確に保持し、計算が要るときは `math/big` の `(*Rat).SetString` で有理数にできる（仕様「数値モデル」、[math/big](https://pkg.go.dev/math/big#Rat.SetString)）。

## 検討した代替案

- **v0.1 全体を一度に実装する**: 構文木の形を早く決めすぎるうえ、パーサーのバグがフォーマッタ・JSON・パス操作のテストに同時に現れる。基礎の上に積むほうが壊れた箇所を絞り込みやすいので、採らない。
- **字句解析とパーサーだけにし、データモデルは後にする**: パースの成功を「エラーがない」としか確かめられず、`Data()` の値も意味規則（重複、型の混ざったリスト）も検査できない。意味規則はパーサーの責務なので、データモデルまで含める。
- **パーサー生成器（goyacc など）や外部ライブラリを使う**: 仕様が標準ライブラリだけを求めている。13 行の LL(1) 文法なら手書きで足り、エラーメッセージと回復を細かく制御できる。
- **構文木を持たず、データモデルだけを作る**: コメントと空行が失われ、フォーマッタと `set`（コメントを残す）を作るときに作り直しになる。

## 影響とトレードオフ

- 得るもの: 字句・構文・意味規則のテストを、ほかの機能の影響なしに固められる。後続の機能は `File` と `Value` にだけ依存すればよい。
- 失うもの: 基礎の段階では `lkal` コマンドがなく、文書の検査には Go のテストかライブラリ呼び出しが要る。
- リスク: フォーマッタを作る段階で、構文木に足りない情報が見つかるかもしれない。そのときは構文木を拡張し、この ADR を更新する。
- 今後: 正準形、LKAL-JSON、パス操作と CLI を、それぞれ ADR にしてから実装する。
