# 0003: 基礎の実装を agy-orch-mcp の antigravity_batch に委譲し、テストを先に書いて RED と GREEN を別コミットにする

## コンテキスト

基礎（[[0001]]）は 6 つのファイルで、トークン規則 13 種、意味規則 7 つ、エラーコード 22 個（[[0002]] の追加を含む）を満たす必要がある。作業者は、ホスト（Claude Code または Codex）と、`agy-orch-mcp` 経由の Google Antigravity CLI（`agy`）である。

agy-orch-mcp の運用方針（agy-first）では、ホストはオーケストレーション専用（Go コードの編集は行わない）とし、タスク分解、指示パケットの作成、最終 diff とエビデンスのレビューに専念し、調査・実装・テスト・自己修正は agy に委ねる。コード変更を伴う並列タスクには `antigravity_batch` を使う。batch は各タスクを隔離した Git worktree で実行し、`owns` の検証とゲートを通った差分を `final.patch` として返す。ホストの作業ツリーは書き換えない。

制約は次の通り。

- batch はクリーンな作業ツリー（未追跡ファイルも含めて変更なし）を要求し、ワーカーに見えるのはコミット済みのファイルだけである。
- 仕様ドラフトは `docs/internal/` に置き、`.gitignore` で除外した（公開リポジトリに載せない）。そのためワーカーの worktree には入らないが、ワーカーはホスト側チェックアウトの明示的な絶対パスから読み取り専用で参照する。非公開の仕様書はコピーもコミットもしない（追跡ドキュメントには個人環境の絶対パスを含めない）。
- batch の worktree は OS の一時ディレクトリに作られ、agy の信頼済みワークスペースに含まれない。ヘッドレスの agy は、許可のないシェルコマンドを 1 つでも出すとそのターンを失う。
- 個人環境に依存する MCP 設定（`.mcp.json`、`.codex/`、`.claude/settings.local.json`）は Git 管理しない。

## 決定

- agy-orch-mcp を MCP サーバー `agy_orch`（batch と fetch を有効化）として、Git 管理外の `.mcp.json` に登録する。
- 実装はテストを先に書いて進め、`antigravity_batch` による 2 つの主 batch を基本とし、レビューやゲートの要求に応じた回数を決めた追加の修復を行う。
    1. **RED batch**: まず 1 タスクで `go.mod` と、[[0001]] の型と関数のシグネチャだけを持つスタブを作る。続けて、テストを並列タスクで書く（字句解析、パーサーとデータモデル、エラーコードと位置、`Equal`、適合テストの `testdata/` と実行器、パニックしないことを見る `FuzzParse`）。ゲートは、テストがコンパイルできることと `gofmt` の出力が空であることで、テストの合格は求めない。
    2. **GREEN batch**: 実装を並列タスクで書く（字句解析と `Equal` を並列にし、パーサーは字句解析の後）。ゲートは `go test -count=1 ./...`、`go vet ./...`、`gofmt -l .` の出力が空であること。ゲートが落ちたら、失敗出力を渡して修復タスクを回す。
- ワーカーはシェルコマンドを使わず、ファイルの読み書きだけを行う。検証はゲートが受け持つ。指示パケットには関連する `docs/internal/agy` の契約（`00-common` と `10-api` は必須）を貼り、ワーカーは `.gitignore` された完全な仕様書をホスト側チェックアウトの明示的な絶対パスから読み取り専用で直接参照する。非公開の仕様書は決してコピーやコミットをしない（追跡ドキュメントには個人環境の絶対パスを含めない）。
- ワーカーのモデルは `gemini-3.8-flash-high`（`tier: "reasoning"`）とする。
- ホストはオーケストレーション専用とし（Go コードの編集は行わない）、各 batch の後に `final.patch` を作業ツリーに当て、テストを自分でも実行する。Opus レビュー（Claude サブエージェント、または読み取り専用の agy 経由の Opus 実行）により差分と仕様を突き合わせてレビューさせ、RED では「テストが仕様どおりか」、GREEN では「テストを弱めていないか」を見る。
- `feat/foundation` ブランチで、RED（テストとスタブ）と GREEN（実装）を別のコミットにする。push はしない。

## 根拠（調査結果・出典）

- agy-orch-mcp の README と AGENTS.md（[Kaikei-e/agy-orch-mcp](https://github.com/Kaikei-e/agy-orch-mcp)）: agy-first の役割分担、指示パケットの 4 要素（ゴール、スコープとファイル所有権、制約・受入基準・テスト計画、エビデンス）、「コード変更を伴う並列タスクは antigravity_batch」、batch のクリーンツリー要件と argv 形式のゲート、個人用 MCP 設定を `.gitignore` に入れる方針が書かれている。
- agy-orch-mcp の `src/workspace/worktree-manager.ts` は、worktree を `os.tmpdir()` 配下の `agy-orch-worktrees/<runId>` に作る。
- agy-orch-mcp の `src/workspace/git-repository.ts` は、`git status --porcelain=v1 --untracked-files=all` で汚れを判定するので、未追跡ファイルが 1 つでもあると batch を拒否する。
- 仕様ドラフト v0.1「Go実装方針」は、テストをゴールデン・性質・ファズ・適合の 4 種と定めている。基礎の範囲では、フォーマッタと JSON に依存するゴールデンと性質テストは後の段階に回し、ファズは「パニックしない」ことだけを確かめる。

## 検討した代替案

- **ホストが直接実装する**: agy-orch-mcp の方針（ホストは分解とレビューに専念する）に反し、「agy-orch-mcp を最大限活用する」というユーザーの指示にも合わない。
- **作業ツリーで `antigravity_run` を直接回す**: ファイル編集だけであれば信頼済みシェルの権限は不要だが、共有作業ツリーでの競合リスクがあり、batch のような owns 検証・隔離・ゲートが得られない。直接実行は読み取り専用レビューや競合しない回数を決めた追加の修復に有用なため、補足手段として残す。
- **テストと実装を 1 回の batch で同時に書く**: RED を確かめる時点がなく、実装に合わせてテストを書く形になりやすい。TDD の意味がなくなる。
- **仕様ドラフトを作業ツリーにコピーまたはコミットしてワーカーに読ませる**: 内部ドキュメントを公開リポジトリに載せることや不要な複製につながる。契約をパケットに貼り、完全な仕様書はホスト側チェックアウトの絶対パスから読み取り専用で参照させるため採らない。

## 影響とトレードオフ

- 得るもの: テストが仕様から先に決まり、実装はゲートで機械的に検証される。並列タスクは worktree で隔離されるので、互いのファイルを壊さない。
- 失うもの: ワーカーは実装中にテストを実行できず、ゲートの失敗出力と修復タスクだけで直す。修復が増えると時間がかかる。
- リスク: agy の報告は事実と違うことがある。差分、テスト件数、仕様の引用は、ホストと Opus レビューで必ず確かめる。テストを通すためにテストを弱める変更は、GREEN のレビューで差し戻す。
- 運用: Claude Code は MCP 設定をセッション開始時にだけ読むので、登録後はセッションの再起動が要る（アクティブな MCP サーバー設定が対象リポジトリと一致していること）。
